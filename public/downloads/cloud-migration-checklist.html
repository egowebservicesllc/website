Cloud Migration Checklist

40 checks our engineers run before moving any business to Google Cloud, AWS or Microsoft Azure. Work through it with your team, or use it to check a partner's proposal.

Tick each item when it's done. Items marked ★ change cost and risk the most, so don't skip them.

1. Goals & inventory

  • Write down why you're moving: cost, scale, reliability, security or a hardware/contract deadline
  • List every server, VM, app, database, file share and scheduled job
  • Map dependencies: which systems must move together
  • Record current usage (CPU, memory, storage, traffic) for at least 2 weeks
  • Note licences (Windows Server, SQL Server, Oracle) and whether they can move
  • Identify owners and decision-makers for each system
  • Agree how much downtime each system can tolerate
  • Set a budget and a target date

2. Platform & design

  • Choose the cloud and region(s) based on customers, regulations and existing software
  • Decide per system: move as-is, re-platform, rebuild or retire
  • Right-size every machine from real usage, not old hardware specs
  • Prefer managed services (databases, Kubernetes, storage) where they reduce work
  • Design networking: VPCs, subnets, private access, VPN or interconnect to the office
  • Plan high availability: multiple zones for anything customer-facing
  • Define environments: production, staging and development
  • Build the foundation as code (Terraform) so it can be repeated and reviewed

3. Security & compliance

  • Set up identity: single sign-on, multi-factor authentication, no shared admin accounts
  • Apply least-privilege roles; separate production access
  • Store secrets and keys in a managed vault, never in code
  • Turn on audit logging and keep logs in a separate, protected place
  • Encrypt data at rest and in transit
  • Check compliance needs (GDPR, HIPAA, PCI DSS, data residency) and document how they're met
  • Put a web application firewall and DDoS protection in front of public apps
  • Enable the cloud's security posture checks and alerts

4. Data & cut-over

  • Take full backups before you start, and test a restore
  • Choose the data-move method: online replication, export/import or physical transfer
  • Rehearse the migration in staging with production-sized data
  • Test performance and load before go-live
  • Write a cut-over runbook with a timed rollback plan
  • Lower DNS TTLs a few days before switching
  • Freeze changes and tell users about the cut-over window
  • Verify data and key business flows right after switching

5. Costs & operations

  • Set budgets and alerts from day one
  • Label every resource by team, environment and project for cost tracking
  • Use discounts for steady workloads (committed-use, savings plans, reserved instances)
  • Schedule non-production environments to switch off out of hours
  • Set up monitoring, uptime checks and on-call alerts
  • Automate backups and patching, and test restores monthly
  • Hand over documentation and train your team
  • Review costs and performance 30 days after go-live, then monthly
